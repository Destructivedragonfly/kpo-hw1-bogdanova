## entities/entities.go

Базовый класс для данных предмета оборудования `base`.

Для транспорта также необходимо знать *простоту*, поэтому мы используем `vehicle`, чтобы расширить функционал. Это **композиция**, так как base встраивается в `vehicle`, ведь нам нужна общая часть у нескольких типов. `gear` аналогично.

## entities/item.go

`Item`- **интерфейс с методами** объекта оборудования. Он нам нужен, чтобы можно было работать с любым предметом в хранилище, не зная, каков его конкретный тип. 

`BeginnerRated` встраивает `Item`, опять используем **композицию**. 

`EnergyConsumer` не встраивает `Item`, потому что (потенциально) потреблять энергию на складе могут не только хранящиеся там предметы.

`Info` - унифицированные данные об объекте, которые нужны фабрике.

## entities/factory.go

### Option и class
`Option` - данные для отображения в меню. Фабрика их хранит, но сама не использует.

Для создания фабрики есть вспомогательная структура `class`. Он *нужен только для регистрации*, чтобы настроить функцию-создателя. 

Казалось бы, между `Option` и `class` различие только в том, что у последнего есть `isConsumer`. Но мы не добавляем `isConsumer` в `Option`, потому что `Option` - публичное описание для меню, ему не нужен для этого `isConsumer`.

### Фабрика
`entry` - встроенный `Option` + функция создания `Creator`. Таким встраиванием мы позволяем данным из `Option` оставаться *публичными*, а функции создания быть *приватной*. 

`Factory` - **фабрика** для создания объектов оборудования, то есть, список из `entry`. Избираем такой паттерн, чтобы было легче расширять типы объектов. У `*Factory` есть два значения: `NewVehicleFactory()`, `NewGearFactory()`. Внутри фабрик `Creator` создаёт уже конкретные объекты.

## infrastructure/inspector.go

Имеется интерфейс проверяющего `Inspector` и структура `ServiceCenter` его реализующая. Такая абстракция необходима для тестируемости и расширяемости видов инспекций.

## infrastructure/storage.go

Аналогично для `Storage` и `CurStorage`. `CurStorage` хранит items и все занятые инвентарные номера, чтобы не допустить их повторения.

## infrastructure/reception.go

`Reception` хранит функцию, которая указывает на то, как определяется можно ли пользоваться объектом новичкам, а также `Storage` и `Inspector`. Итого, всё необходимое для того, чтобы обрабатывать новые объекты и давать информацию по старым (структура `Report`).

## interaction/console.go
`console` используется всякого рода подготовки и обработки ввода. 
```
type console struct {
	in   *bufio.Reader // буферизированный ввод, чтобы сэкономить вызовы
	echo bool // отвечать ли эхом на каждый запрос
	out  io.Writer
}
```

## interaction/app.go

`App` реализует главные процессы. В него встраивается `Info`, оно именно встраивается, а не является полем для более читаемого обращения к его полям. Также `Info` в целом отдельно, чтобы его можно было легко подменить.  

# Ответы на вопросы

## 1. Какой принцип SOLID применён наиболее явно?

**DIP (инверсия зависимостей)** `Reception` (`infrastracture/reception.go`) не знает ни конкретного хранилища, ни конкретного проверяющего. Он получает интерфейсы `Storage`, `Inspector` и `BeginnerRule` через конструктор `New(storage, inspector, rule)`.

Конкретные `CurStorage`, `ServiceCenter` и `CheckIsSimpl(min)` собираются в одном месте - `run` в `main.go`. `App` тоже получает всё готовым через `interaction.Info`.

Рядом идёт **ISP**: интерфейсы `Item`, `BeginnerRated`, `EnergyConsumer` (`entities/item.go`) маленькие, поэтому `gear` не обязан иметь простоту.

## 2. Какой принцип сознательно ограничен?

**OCP (открытость/закрытость)** Новый вид оборудования добавляется не привычным расширением, а правкой одной таблицы: надо дописать `class` и `entry` в `NewVehicleFactory`/`NewGearFactory` (`entities/factory.go`). Это приемлемо, изменение локально, а `Reception`, `Report` и `App` не меняются. Что-то более сложное было бы избыточным.

Также приходится делать проверку `item.(BeginnerRated)` / `item.(EnergyConsumer)` - это осознанная плата за то, что `Item` остаётся маленьким интерфейсом.

## 3. Что сломается при расширении?

**Новый вид транспорта** Одна запись `class` + `entry` в `NewVehicleFactory`. Если пункт вставлен не в конец, сдвигаются номера видов в меню, поэтому нужно переписывать `demo.txt` и `demo_test.go`. 

**Склад запчастей** Второй экземпляр `Storage` (интерфейс уже есть). Проблема в том, что `Info` не масштабируется на разные категории с разными полями. А также у `Reception` сохранятся поля, которые не обязательно нужны новому классу.

## 4. Какой тест фиксирует решение техосмотра и правило для новичков, как подменяется зависимость?

### Техосмотр
`TestInspect` (три случая: принят, отказ, превышение лимита энергии) и `TestExam` (принятое попадает на склад, отклонённое - нет, дубль даёт `ErrDuplicateNum`) в `infrastracture/infrastracture_test.go`.

### Правило новичков
`TestBeginners` там же: порог включительный (`>= 6`), транспорт с простотой 5 не попадает в список, снаряжение не попадает никогда. Проверка на демо - `TestDemoBeginners` и `TestFlagMinSimpl` в `demo_test.go`.

### Подмена зависимостей
В тестах `Reception` собирается через `New(NewCurStorage(), ServiceCenter{MaxEnergyKWh: 5}, CheckIsSimpl(6))`: порог и лимит задаются параметрами, а правило новичков - просто другой функцией `BeginnerRule`. Вместо `ServiceCenter` можно передать любую структуру с методом `Inspect(item, result bool) ExamResult` (например, заглушку), а вместо `CurStorage` любую реализацию `Storage`.

В `interaction_test.go` подменяются фабрики: в `newApp` создаются свои `entities.NewFactory()` с одним видом, поэтому тест не зависит от реального набора видов. Однако! заглушки `Inspector` в тестах пока нет, используется настоящий `ServiceCenter` с параметрами.
